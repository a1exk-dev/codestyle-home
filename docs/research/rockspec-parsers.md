# Can a plugin's rockspec make lazy.nvim install its Tree-sitter parsers?

Research for issue [#62](https://github.com/a1exk-dev/codestyle-home/issues/62) (parent [#15](https://github.com/a1exk-dev/codestyle-home/issues/15)). It feeds [#14](https://github.com/a1exk-dev/codestyle-home/issues/14): how does a user install the Core and the Language Plugins they want in one step?

Question: a Language Plugin declares its parsers in its spec (`parsers`, Core ADR-0007), but Core ADR-0002 rules out that the Core downloads or compiles parsers. If the Language Plugin's repo has a `*-scm-1.rockspec` whose `dependencies` name parser rocks such as `tree-sitter-php`, does lazy.nvim install them, with no C compiler and no `tree-sitter` CLI, and put the parser where Neovim finds it (`parser/php.so` on the runtimepath)? Is it the same on Linux, macOS and Windows? What changes with a `lazy.lua` in the same repo, next to nvim-treesitter, with LazyVim, rocks.nvim or `vim.pack`? Which plugins already do this?

Date of research: 2026-11-17. This builds on two earlier notes in the Core repo, `docs/research/luarocks-publishing.md` (branch `research/luarocks-publishing`) and `docs/research/one-step-install.md` (branch `research/one-step-install`), and does not repeat them. Sources: lazy.nvim `v11.17.5` (`85c7ff3`), luarocks-build-treesitter-parser `v6.1.1` (`d68f24c`), the `tree-sitter-php` `0.0.55-1` rockspec on luarocks.org, the rocks-binaries and luarocks.org `manifest-5.1` files as served on this date, rocks.nvim `v2.49.1` (`e41cd82`), LazyVim `v16.0.2` (`0fa4a84`), nvim-treesitter `main` (`b706d64`), neorg `v9.6.4` (`a09e0bb`), rest.nvim `v3.13.0` (`de9726a`), the Neovim `v0.12.6` runtime. Terms follow the Core's `GLOSSARY.md`. This note gives facts and no design.

## Answer

- **No. With default settings, lazy.nvim never puts a parser rock where Neovim finds it.** Even when it installs the parser, it adds the rock tree's `lib/lua/5.1` only to `package.cpath`, never to the runtimepath. `vim.treesitter.language.add("php")` then fails with `No parser for language "php"`. All five lazy.nvim runs below ended that way.
- **What lazy.nvim does depends on the rest of the rockspec, not on the parser:**
  - *A plugin with `lua/`, a simple build, and only `lua` and `tree-sitter-*` dependencies* (a plain Language Plugin): lazy.nvim never runs LuaRocks. Its generated name→repo map turns `tree-sitter-php` into the Git plugin `tree-sitter/tree-sitter-php`, so it clones the grammar's C source repo as a plugin. That repo has no `parser/` directory, so Neovim finds no parser.
  - *Any other plugin* (a dependency that is not a Neovim plugin, a `builtin` build with `modules`, or no `lua/`): lazy.nvim builds it with `build = "rockspec"`. It first runs `luarocks install <package> --server rocks-binaries`, which installs the plugin's **published** rock from luarocks.org, with prebuilt parser rocks. This needs no C compiler and no `tree-sitter` CLI. If the package is not published, it runs `luarocks make --dev` in the repo, which builds the parser from source and needs both. In this sandbox the `make` path failed before it reached the parser.
- **The prebuilt parser lands in `<stdpath("data")>/lazy-rocks/<plugin>/lib/lua/5.1/parser/php.so`**, and in the rock's own folder `lib/luarocks/rocks-5.1/tree-sitter-php/0.0.55-1/parser/php.so`, which also holds `queries/php/*.scm`. A plugin can load it with `package.searchpath("parser.php", package.cpath)` and `vim.treesitter.language.add("php", { path = … })`. neorg does exactly this. The queries are not found that way.
- **Without a system `luarocks`, lazy.nvim uses hererocks, which compiles Lua 5.1 and LuaRocks from source.** With no C compiler on `PATH`, that build failed (`couldn't run gcc … is gcc in PATH?`), and so did the plugin's build.
- **Platforms differ.** rocks-binaries holds `tree-sitter-*` rocks for `linux-x86_64` (329 of 332), `macosx-aarch64` (328) and `win32-x86_64` (321, but only 176 at the newest luarocks.org version). It has none for `linux-aarch64` or Intel macOS (`macosx-x86_64`). On those platforms, and wherever the binary is older than luarocks.org's source rock, LuaRocks builds the parser from source. For `tree-sitter-php`, Windows has binaries for `0.0.51-1` and `0.0.52-1` only, while luarocks.org has `0.0.55-1`. Only Linux x86_64 was tested.
- **A `lazy.lua` in the same repo hides the rockspec completely.** The first package source that answers wins, and `lazy` comes before `rockspec`. Tested: with `lazy.lua` next to the rockspec, the plugin's package source is `lazy`, and nothing from the rockspec is installed.
- **Next to nvim-treesitter, the first loaded parser wins for the session.** `language.add` returns early when the language is already registered. Without a `path`, it takes the first `parser/php.*` on the runtimepath, which is nvim-treesitter's `stdpath("data")/site/parser/php.so`, because the lazy-rocks tree is not on it.
- **LazyVim changes nothing here.** Its source does not set `rocks` or `pkg.sources`, and it installs parsers through nvim-treesitter `main` (`ensure_installed`, `:TSUpdate`), which needs the `tree-sitter` CLI and a C compiler.
- **rocks.nvim does what the question asks**, but only for rocks that it installs from a LuaRocks server. It symlinks each installed rock's folder into `site/pack/luarocks/opt/<rock>` and `packadd`s it, so `parser/<lang>.so` and `queries/` are on the runtimepath, and it pulls binaries from rocks-binaries. **`vim.pack` does nothing with a rockspec.**
- **Known plugins whose rockspec names a parser rock:** neorg (`tree-sitter-norg`, `tree-sitter-norg-meta`) and rest.nvim (`tree-sitter-http`). Both have dependencies that are not Neovim plugins, so lazy.nvim builds them with LuaRocks. neorg finds its parser on `package.cpath` with its own code. rest.nvim's lazy.nvim instructions add `http` to nvim-treesitter's `ensure_installed` instead. zeta.nvim names parser rocks only in `test_dependencies`.

- Directly, with no `gcc`, `cc`, `make` or `tree-sitter` on `PATH`: `luarocks --tree T --server https://lumen-oss.github.io/rocks-binaries/ --lua-version 5.1 install --deps-mode one tree-sitter-php` succeeded. It installed `tree-sitter-php-0.0.55-1.linux-x86_64.rock` and `tree-sitter-php_only-0.0.59-1.linux-x86_64.rock`, and wrote `T/lib/lua/5.1/parser/{php,php_only}.so` and `T/lib/luarocks/rocks-5.1/tree-sitter-php/0.0.55-1/{parser/php.so,queries/php/*.scm}`.
- `nvim --clean` with either `…/lib/lua/5.1` or the rock's folder prepended to the runtimepath: `language.add("php")` returned `true`, and a string parser returned a `program` root.
- In run e's setup: `package.searchpath("parser.php", package.cpath)` returned the `lazy-rocks/…/parser/php.so` path, and `language.add("php", { path = it })` returned `true`. `vim.treesitter.query.get("php", "highlights")` returned nil.

## lazy.nvim

- **Package sources.** `pkg.update` asks the sources in `pkg.sources` order (`lazy`, `rockspec`, `packspec`) and stops at the first one that returns a spec. The `rockspec` source is skipped when `rocks.enabled` is false ([`lua/lazy/pkg/init.lua` L32–71](https://github.com/folke/lazy.nvim/blob/v11.17.5/lua/lazy/pkg/init.lua#L32-L71)).
- **Rockspec dependencies become Git plugins when lazy.nvim knows their repo.** For each dependency, `M.get` looks the name up in `lazy.community`. A hit adds `{ url }` as a plugin spec and drops the name from the rocks list ([`lua/lazy/pkg/rockspec.lua` L286–305](https://github.com/folke/lazy.nvim/blob/v11.17.5/lua/lazy/pkg/rockspec.lua#L286-L305)). The map comes from a build script that takes every luarocks.org rock whose name contains `nvim`, `treesitter`, `tree-sitter`, `cmp` or `neo`, and stores the GitHub repo of its `source.url` ([`lua/lazy/build.lua` L8, L71–133](https://github.com/folke/lazy.nvim/blob/v11.17.5/lua/lazy/build.lua#L71-L133)). So the map holds the parser rocks too, for example `tree-sitter-php` → `tree-sitter/tree-sitter-php` ([`lua/lazy/community/_generated.lua` L1983–1986](https://github.com/folke/lazy.nvim/blob/v11.17.5/lua/lazy/community/_generated.lua#L1983-L1986)). That is the grammar's source repo, not a built parser.
- **When LuaRocks runs.** `build = "rockspec"` is set only when the plugin has no `lua/` directory, has a dependency that is neither in the map nor `lua`, or has a build other than `none` or `builtin` without `modules`. Otherwise the result holds only the mapped plugin specs, with `build = false` ([`rockspec.lua` L307–343](https://github.com/folke/lazy.nvim/blob/v11.17.5/lua/lazy/pkg/rockspec.lua#L307-L343)).
- **What LuaRocks runs.** First `luarocks --tree <rocks.root>/<plugin> --server <rocks.server> --lua-version 5.1 install --force-fast --deps-mode one <rockspec.package>`, with the comment "use install so that we can make use of pre-built rocks". This installs the package by name from a server, not the cloned repo. If it fails: `luarocks --tree … --dev --lua-version 5.1 make --force-fast --deps-mode one` in the plugin folder, without `--server` ([`rockspec.lua` L168–214](https://github.com/folke/lazy.nvim/blob/v11.17.5/lua/lazy/pkg/rockspec.lua#L168-L214)). Defaults: `rocks.root = stdpath("data") .. "/lazy-rocks"`, `rocks.server = "https://lumen-oss.github.io/rocks-binaries/"`, `hererocks = nil` ([`lua/lazy/core/config.lua` L59–68](https://github.com/folke/lazy.nvim/blob/v11.17.5/lua/lazy/core/config.lua#L59-L68)).
- **hererocks** runs `hererocks.py -l 5.1 -r latest` into `<rocks.root>/hererocks`. On Windows lazy.nvim then calls `luarocks.bat` ([`rockspec.lua` L32–52, L137–157](https://github.com/folke/lazy.nvim/blob/v11.17.5/lua/lazy/pkg/rockspec.lua#L32-L52)). hererocks builds Lua from source (run c log: `Building Lua 5.1.5`, `Building LuaRocks 3.13.0`).
- **What goes on the paths.** For a plugin whose package source is `rockspec`, the loader calls `add_to_luapath`. It appends `<root>/share/lua/5.1/?.lua`, `?/init.lua`, and `<root>/lib/lua/5.1/?.so` (`.dll` on Windows) and `<root>/lib64/lua/5.1/?.so` to `package.path` and `package.cpath`. Nothing in the rock tree goes on the runtimepath ([`lua/lazy/core/loader.lua` L348–350, L496–505](https://github.com/folke/lazy.nvim/blob/v11.17.5/lua/lazy/core/loader.lua#L496-L505)).

## Where a parser rock puts the parser

- The `tree-sitter-php` `0.0.55-1` rockspec depends on `tree-sitter-php_only == 0.0.59`, has the build dependency `luarocks-build-treesitter-parser >= 6.0.2`, and uses `build.type = "treesitter-parser"` with `lang = "php"`, `generate = false` and `copy_directories = { "queries" }` ([luarocks.org](https://luarocks.org/tree-sitter-php-0.0.55-1.rockspec)).
- The back end refuses to build without the `tree-sitter` CLI ("'tree-sitter CLI' is not installed"), runs `tree-sitter build -o <lib_dir>/parser/<lang>.<ext>`, and copies the `.so`/`.dll` into `<install_dir>/parser`, "for neovim plugin managers that do not symlink the parser directory" ([`src/luarocks/build/treesitter-parser.lua` L201–282](https://github.com/lumen-oss/luarocks-build-treesitter-parser/blob/v6.1.1/src/luarocks/build/treesitter-parser.lua#L201-L282)). `tree-sitter build` compiles C, so it needs a C compiler.
- A binary rock from rocks-binaries skips that build. LuaRocks deploys the rock's `lib/parser/php.so` to `<tree>/lib/lua/5.1/parser/php.so` and keeps a copy in `<tree>/lib/luarocks/rocks-5.1/tree-sitter-php/0.0.55-1/parser/`, next to `queries/php/` (observed above).
- Neovim looks for parsers only on the runtimepath: `language.add` without `path` takes the first `parser/<lang>.*` from `nvim_get_runtime_file`, and returns `true` at once if the language is already registered ([Neovim `runtime/lua/vim/treesitter/language.lua` L107–143](https://github.com/neovim/neovim/blob/v0.12.6/runtime/lua/vim/treesitter/language.lua#L107-L143)).

## Platforms

Counts from the rocks-binaries `manifest-5.1` against luarocks.org's `manifest-5.1` on 2026-11-17. "Newest" means the rock has a binary for the newest non-`scm` version that luarocks.org lists.

| Arch | `tree-sitter-*` rocks with a binary (of 332) | with a binary for the newest version |
| --- | --- | --- |
| `linux-x86_64` | 329 | 326 |
| `macosx-aarch64` | 328 | 325 |
| `win32-x86_64` | 321 | 176 |
| `macosx-x86_64` | 0 | 0 |
| `linux-aarch64` | 0 | 0 |

luarocks.org lists 347 `tree-sitter-*` rocks. rocks.nvim's README says the parsers are uploaded only if "we can install [them] in the NURR CI (tested on Linux)". It also says that on other architectures rocks.nvim "will attempt to compile its dependencies instead of pulling a pre-built binary" ([rocks.nvim README L128–131, L187–193](https://github.com/lumen-oss/rocks.nvim/blob/v2.49.1/README.md)). Not tested here: an unversioned `tree-sitter-php` dependency on Windows. luarocks.org has the `0.0.55-1` source rock and rocks-binaries has `0.0.52-1` at most for `win32-x86_64`. LuaRocks normally picks the highest version that matches, which would be the source rock.

## Next to nvim-treesitter, and LazyVim

- nvim-treesitter `main` installs into `install_dir`, by default `stdpath("data")/site`, which is on the runtimepath, so its parsers are `site/parser/<lang>.so` ([`lua/nvim-treesitter/config.lua` L10–19](https://github.com/nvim-treesitter/nvim-treesitter/blob/b706d642dd20d0922e7e92365dc73617f0fdb4ea/lua/nvim-treesitter/config.lua#L10-L19)). It requires `tree-sitter-cli` 0.26.1 or later and a C compiler ([README L17–22](https://github.com/nvim-treesitter/nvim-treesitter/blob/b706d642dd20d0922e7e92365dc73617f0fdb4ea/README.md#L17-L22)).
- A lazy.nvim parser rock is not on the runtimepath, so `language.add(lang)` without a path always finds nvim-treesitter's copy or nothing. Code that passes `path` (neorg) registers the rock's copy if it runs first. After that, the language is registered and every later `add` returns `true` without loading anything.
- rocks.nvim's health check reports an error when `tree-sitter-<lang>` rocks and nvim-treesitter `master` are both installed: "'nvim-treesitter' (master) conflicts with luarocks 'tree-sitter-<lang>' parsers" ([`lua/rocks/health.lua` L165–186](https://github.com/lumen-oss/rocks.nvim/blob/v2.49.1/lua/rocks/health.lua#L165-L186)).
- LazyVim `v16.0.2` has no `rocks` setting in its source. Its only `pkg` use is `pkg = false` while it parses extras for its extras browser ([`lua/lazyvim/util/extras.lua` L88–95](https://github.com/LazyVim/LazyVim/blob/v16.0.2/lua/lazyvim/util/extras.lua#L88-L95)). Its Tree-sitter spec uses nvim-treesitter `main` with `ensure_installed` and `:TSUpdate` ([`lua/lazyvim/plugins/treesitter.lua` L11–33](https://github.com/LazyVim/LazyVim/blob/v16.0.2/lua/lazyvim/plugins/treesitter.lua#L11-L33)). The LazyVim starter's `lua/config/lazy.lua` (`803bc18`) sets no `rocks` either.

## rocks.nvim and `vim.pack`

- rocks.nvim appends `<rocks_path>/rocks_rtp` to the runtimepath. For each installed rock, it symlinks `<rocks_path>/lib/luarocks/rocks-5.1/<rock>/<version>` to `stdpath("data")/site/pack/luarocks/opt/<rock>` and `packadd`s it ([`lua/rocks/adapter.lua` L27–32, L108–155](https://github.com/lumen-oss/rocks.nvim/blob/v2.49.1/lua/rocks/adapter.lua#L108-L155); [`lua/rocks/runtime.lua` L37–56](https://github.com/lumen-oss/rocks.nvim/blob/v2.49.1/lua/rocks/runtime.lua#L37-L56)). That folder holds `parser/` and `queries/`, so Neovim finds both.
- Its README: "specifying a tree-sitter parser as a dependency is now as straightforward as including it in their project's rockspec", with the example `dependencies = { "neotest", "tree-sitter-haskell" }`. It also says "you don't even need to compile any parsers on your machine" because it searches rocks-binaries ([README L131–176](https://github.com/lumen-oss/rocks.nvim/blob/v2.49.1/README.md)). rocks.nvim reads the rockspec of the rock it installs from a server (luarocks.org), not a rockspec in a Git repo. The rocks-git.nvim README does not mention rockspecs.
- `vim.pack` (Neovim 0.12) clones Git repos and has no rockspec or LuaRocks support. Its help shows build steps only as user code in a `PackChanged` autocommand, for example `vim.system({ 'make' }, …)` ([`runtime/doc/pack.txt` L362–399](https://github.com/neovim/neovim/blob/v0.12.6/runtime/doc/pack.txt#L362-L399)).

## Plugins that already name parser rocks

A GitHub code search for `tree-sitter-` in `.rockspec` files (2026-11-17, first 100 hits; most hits are the parser rocks themselves and a luarocks mirror) found three Neovim plugins:

| Plugin | Rockspec dependency | lazy.nvim path | How the parser is found |
| --- | --- | --- | --- |
| neorg (7.5k stars) | `tree-sitter-norg == 0.2.4`, `tree-sitter-norg-meta == 0.1.0`, plus `nvim-nio`, `lua-utils.nvim`, `nui.nvim`, `pathlib.nvim` ([`neorg-scm-1.rockspec` L13–23](https://github.com/nvim-neorg/neorg/blob/v9.6.4/neorg-scm-1.rockspec#L13-L23)) | `build = "rockspec"`; published as `neorg` on luarocks.org, so `luarocks install` gets binary parsers. The README tells lazy.nvim users to "ensure that you have `luarocks` installed" (L113–125). | `package.searchpath("parser." .. lang, package.cpath)`, then `vim.treesitter.language.add(lang, { path = path })`. It warns only if no `parser/<lang>.so` is on the runtimepath either ([`lua/neorg/modules/core/integrations/treesitter/module.lua` L59–74](https://github.com/nvim-neorg/neorg/blob/v9.6.4/lua/neorg/modules/core/integrations/treesitter/module.lua#L59-L74)) |
| rest.nvim (2.1k stars) | `tree-sitter-http == 0.0.35`, plus `nvim-nio`, `mimetypes`, `xml2lua`, `fidget.nvim` ([`rest.nvim-scm-1.rockspec` L22–29](https://github.com/rest-nvim/rest.nvim/blob/v3.13.0/rest.nvim-scm-1.rockspec#L22-L29)) | `build = "rockspec"` | The README lists "[tree-sitter-http] (if you use `lazy.nvim`)" as a dependency and its lazy.nvim spec adds `"http"` to nvim-treesitter's `ensure_installed` ([README L45–77](https://github.com/rest-nvim/rest.nvim/blob/v3.13.0/README.md)) |
| zeta.nvim (51 stars) | `tree-sitter-lua`, `tree-sitter-rust` only in `test_dependencies` | not affected | n/a |

None of the three has a `lazy.lua`.
